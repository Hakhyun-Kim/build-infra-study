## 이 챕터의 목표

"테스트를 자동으로 돌린다"에서 "**테스트 결과를 믿을 수 있다**"로 넘어가는 데 필요한 것들.
계층을 나누는 것까지는 누구나 한다. 그다음 세 가지가 실무를 가른다.

1. 무엇을 어느 계층에 넣을 것인가 (**배분 규칙**)
2. 아래 계층 결과가 위 계층을 얼마나 예측하는가 (**신뢰도 측정**)
3. 실패했을 때 무엇이 남는가 (**재현 번들**)

## 디바이스 팜이 실패하는 이유 (실기기 특유)

소프트웨어 테스트와 다른 점은 **디바이스가 상태를 갖는다**는 것이다.

- 이전 테스트가 남긴 파일·설정
- 플래싱 실패로 반쯤 죽은 보드
- 열, 전원, USB 연결 불안정
- 여러 잡이 같은 보드를 동시에 잡는 경쟁

→ 그래서 팜에는 **health check, 전원 사이클링, 초기 상태 복원, 배타적 예약**이 필요하다.
LAVA가 이 문제들을 어떻게 모델링했는지 보는 것이 지름길.

> 💡 **일반화**: "하드웨어가 물려 있는 자동 테스트"의 실패 양상은 도메인이 달라도 비슷하다.
> 소비자 기기, 로봇, 임베디드 보드 어느 쪽이든 디바이스가 상태를 갖는 순간 같은 문제가 나온다.
> 다른 도메인에서 본 실패 양상이 있다면 여기에 대조해서 정리해두면 좋다.

## 열린 질문

- [ ] flaky를 **어떻게 정의**할 것인가? (같은 커밋 N회 재실행 중 실패율?)
- [ ] flaky 테스트를 격리하면 커버리지가 조용히 줄어드는데, 그건 어떻게 관리하나?
- [x] **선별의 진짜 위험은 과다 선택이 아니라 과소 선택이다.** BUILD 파일을 바꾼 커밋에
      대해 파일 단위 `rdeps`는 `Empty results`를 준다 — 테스트를 하나도 안 돌리고 초록불.
      그래프 정의 파일(BUILD/.bzl/.bazelrc/MODULE.bazel/툴체인)을 만나면 전체로 폴백해야 한다. (exp05)
- [ ] 선별 실행이 놓친 실패를 야간 전체 실행이 잡은 비율 — 이걸 어떻게 자동 집계하나?
- [ ] 실패 재현 번들에 최소한 무엇이 들어가야 하는가?
- [ ] 실기기 팜의 처리량을 늘리는 것과 가상 팜의 정확도를 높이는 것, 어느 쪽이 싼가?
