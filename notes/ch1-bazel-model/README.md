# ch1 — Bazel의 모델

> 대응 실험: [exp01](../../experiments/exp01_bazel_hello/), [exp02](../../experiments/exp02_remote_cache/)

## 이 챕터의 목표

CMake를 오래 쓴 사람이 Bazel에서 헷갈리는 건 문법이 아니라 **모델**이다.
"왜 시스템 라이브러리를 마음대로 못 쓰지?"에 스스로 답할 수 있으면 이 챕터는 끝난 것이다.

## 액션 그래프 — 기존 빌드 도구와 무엇이 다른가

한 줄로: **make와 MSBuild는 "어떻게 만들지"를 적은 스크립트를 실행하고,
Bazel은 "무엇을 만들지"를 데이터 구조로 먼저 완성한 뒤 그걸 실행한다.**

### 액션이 실제로 무엇인가

Bazel의 액션 하나는 문자열 명령이 아니라 구조체다:

```
action = {
  inputs:   [파일 목록 + 각각의 내용 해시]
  outputs:  [만들어낼 파일 목록]
  argv:     [실행할 명령줄]
  env:      [환경변수 - strict면 고정, 아니면 호스트에서 상속]
  platform: [어느 툴체인 / 실행 환경]
}
```

**입력 집합이 완전하게 선언되어 있다**는 것이 뒤따르는 모든 기능의 전제다.

- 액션 전체의 **해시**를 계산할 수 있다 → 캐시 키
- 입력만 담긴 **샌드박스**를 만들 수 있다 → 미선언 의존성이 즉시 실패
- 입력을 **다른 머신으로 전송**할 수 있다 → 원격 실행
- 실행 전에 **그래프에 질의**할 수 있다 → `aquery`, 변경 영향 분석

make의 레시피는 셸 문자열이라 이 중 무엇도 못 한다. make는 그 명령이 실제로 무슨
파일을 읽는지 **모르고**, 사람이 적어준 의존성 목록을 믿을 뿐이다.

### 비교

| | make | MSBuild / vcbuild | ninja (CMake 생성) | Bazel |
|---|---|---|---|---|
| 그래프의 정체 | Makefile 자체, 레시피는 불투명 문자열 | XML Item/Target, 태스크는 불투명 | 생성된 .ninja 파일 | **메모리 안의 액션 객체 그래프** |
| 그래프를 누가 만드나 | 사람이 손으로 | 사람 + IDE | CMake가 생성 | Bazel이 분석 단계에서 |
| 재빌드 판단 | **mtime 비교** | mtime + `.tlog`(명령줄 포함) | mtime + 명령줄 해시 | **내용 해시 + 액션 전체 해시** |
| 헤더 의존성 | 손으로 쓰거나 `-MMD` 곁다리 | FileTracker가 실제 접근 기록 | 컴파일러 depfile | **선언 + 샌드박스로 강제** |
| 미선언 의존성 | 조용히 통과 (나중에 터짐) | 대개 통과 | 대개 통과 | **빌드 실패** |
| 캐시 공유 | 없음 (ccache 곁다리) | 없음 | 없음 (ccache 곁다리) | **설계의 중심** |
| 원격 실행 | 불가 | IncrediBuild 등 외부 도구 | 불가 | **내장** |
| 그래프 질의 | 불가 | 불가 | `ninja -t deps` 정도 | **query / cquery / aquery** |
| 빌드 경계 | recursive make로 쪼개짐 | 프로젝트·솔루션 단위 | 하나 | **전체가 하나의 그래프** |

### 갈리는 지점을 실측으로 (exp02)

**컴파일러 플래그만 바꿨을 때** — `--copt=-O2` 추가, 소스는 그대로:

```
29.63s, 캐시 히트 0  ->  82개 전부 재컴파일
```

Makefile에서 `CFLAGS`를 바꾸면 `make`는 **아무것도 다시 만들지 않는다.** mtime이
안 바뀌었기 때문이다. 다들 `make clean`을 반사적으로 치는 습관 자체가 make의
정확성 모델이 불완전하다는 증거다. MSBuild는 `.tlog`에 명령줄을 기록해서 이건
잡아내고(이 항목만큼은 make보다 낫다), ninja도 명령줄 해시를 비교한다.

**`touch`만 했을 때** — 내용 동일:

```
0.51s, 82개 전부 캐시 히트  ->  아무것도 재컴파일 안 함
```

make는 무조건 다시 만든다. 대규모 프로젝트에서 `git checkout`으로 브랜치를 오갈
때마다 전체 재빌드가 일어나는 이유가 이것 — 내용은 원래대로 돌아왔는데 mtime만
새것이 된 상황이다.

### 그래프가 있어야만 가능한 것

1. **공유 캐시.** 액션 키가 내용 해시라 **다른 머신에서도 같은 키**가 나온다.
   동료가 이미 컴파일한 결과를 그대로 받아 쓸 수 있다. make/MSBuild 산출물은
   절대 경로와 로컬 상태에 묶여 공유가 안 된다(ccache가 컴파일 단계만 흉내내는 이유).
   단 **hermetic해야만 성립한다** — exp02에서 strict를 끄자 `PATH` 하나로 히트가 0이 됐다.
2. **변경 영향 분석.** "이 커밋이 어떤 테스트에 영향을 주는가"를 그래프에 물을 수 있다(exp05).
   MSBuild 솔루션에서는 신뢰성 있게 답할 방법이 없다.
3. **크로스 빌드가 설정 변경으로 끝난다.** BUILD 파일을 안 고치고 `--platforms`만 바꾸면
   같은 타깃이 다른 configuration으로 그래프에 다시 배치된다 — exp03에서 소스 한 줄
   안 고치고 aarch64 바이너리를 얻었다.
   ⚠️ 단 **출력 디렉터리는 기본적으로 분리되지 않는다.** 디렉터리 이름이 레거시 `--cpu`
   값에서 오기 때문에 둘 다 `bazel-out/k8-fastbuild/`로 들어가 서로를 덮어쓴다.
   `--experimental_platform_in_output_dir`가 필요하다 (exp03에서 실측).
4. **전체가 하나의 그래프.** recursive make는 하위 make마다 부분 그래프만 알아서
   병렬성과 정확성이 동시에 망가진다("Recursive Make Considered Harmful"의 그 문제).

### 대가

공짜가 아니다. 정확히 적어둔다.

- **전부 선언해야 한다.** 시스템 라이브러리를 그냥 include하고 링크하는 게 안 된다.
  서드파티마다 규칙을 만들거나 가져와야 한다.
- **마이그레이션 비용이 크다.** 기존 CMake/MSBuild 프로젝트를 옮기는 건 몇 달짜리 일이다.
- **배포가 제한된 툴체인과 hermetic 원칙이 충돌한다** (콘솔 SDK 등) — 아래 열린 질문 참조.

**판단 기준:** 빌드가 작고 한 머신에서 끝나면 make/CMake가 낫다.
타깃이 수천 개, 사람이 수십 명, 아키텍처가 여럿이고 **캐시를 공유해야 한다면**
그때부터 Bazel의 제약이 값을 한다. 빌드 팜은 여러 머신이 같은 작업을 중복하지
않아야 성립하고, 그건 내용 주소 기반 캐시 없이는 불가능하다.

## 열린 질문 (실험으로 답할 것)

- [x] **재빌드 판단은 mtime이 아니라 내용 해시다** — `touch`만 하면 재컴파일이 일어나지 않는다
      (exp01에서 확인). CMake/make 계열과 갈리는 첫 지점.
- [x] **액션 키에 들어가는 것**: 소스의 **내용 해시**(mtime 아님), **컴파일러 플래그**
      (`--copt=-O2`만 붙여도 82개 전부 미스), strict를 끄면 **환경변수**까지.
      `-O2` 판과 기본 판은 캐시에 **공존**한다 — 서로를 밀어내지 않는다. (exp02)
- [x] **`--incompatible_strict_action_env`를 끄면**: `PATH` 앞에 디렉터리 하나만 추가해도
      캐시 히트가 0이 된다(16.8초 전량 재컴파일). 켜두면 0.66초에 82개 전부 히트.
      → 공유 캐시가 안 듣는다는 신고가 오면 **여기부터 본다**. (exp02)
- [ ] 캐시가 "잘못 맞는" 오염 상황을 인위적으로 만들 수 있는가?
      (절대 경로 / `__DATE__` / 호스트 툴체인 버전 중 무엇이 가장 쉽게 재현되는가)
- [x] `bazel clean`은 출력만, `--expunge`는 외부 의존성·툴체인 탐지까지 날린다.
      캐시 측정에는 `clean`이 맞다 — `--expunge`는 재탐지 시간이 노이즈로 섞인다. (exp02)
- [x] **`query`는 `select()`의 모든 분기를 보여준다** — 리눅스에서 빌드했는데 deps에
      `host_windows`, `def_parser.exe`가 나왔다. config를 반영하려면 `cquery`.
      exp05에서 `query`로 영향 테스트를 고르면 과다 선택이 될 수 있다는 뜻.
- [ ] 게임 엔진처럼 플랫폼이 여럿인 대규모 C++ 빌드에 Bazel을 쓴다면 무엇이 문제가 될까?
      (콘솔 SDK처럼 배포가 제한된 툴체인은 hermetic 원칙과 어떻게 충돌하는가)


## 측정 자체에 대한 교훈 (exp02에서 얻은 것)

**작은 프로젝트로 캐시를 측정하면 아무것도 못 잰다.** exp01의 소스 3개로 재보니
1.33초 → 0.62초, 2.2배였는데 이건 캐시 효과가 아니라 고정 오버헤드(분석 0.15초 +
서버 왕복)를 본 것이다. 컴파일이 지배하는 워크로드(40 라이브러리)로 바꾸자
15.5초 → 0.5초, **28.9배**가 나왔다.

성능 측정에서는 늘 같은 질문을 먼저 해야 한다 — **내가 재려는 것이 전체 시간의 몇
퍼센트인가.** 그게 10%라면 아무리 개선해도 10% 넘게 못 줄인다.
