# exp07 — ci_pipeline

## 질문

exp01~05를 **파이프라인 하나로** 엮고, 계층별 소요 시간을 측정할 수 있는가.
그리고 각 계층은 **어떤 실패를 잡도록 설계되어야 하는가.**

계층을 나누는 건 쉽다. 어려운 건 **무엇을 어느 계층에 넣느냐**와
**아래 계층 결과를 얼마나 믿을 수 있느냐**다.

## 방법

GitLab CI로 짠다 (사내 온프렘 CI에서 흔한 선택). 로컬 러너로 돌려본다.

```bash
# gitlab-runner 로컬 설치 후
gitlab-runner exec docker <job-name>   # 또는 로컬 GitLab 인스턴스
```

목표 파이프라인:

| 단계 | 내용 | 목표 시간 | 잡아야 하는 실패 |
|---|---|---|---|
| L0 pre-commit | 포맷·린트 | < 10s | 스타일, 명백한 실수 |
| L1 host build+test | 호스트 아키텍처 빌드·단위 테스트 | < 2min | 로직 오류 |
| L2 cross build | aarch64 크로스 빌드 | < 5min | 타깃 전용 컴파일 오류, ABI |
| L3 virtual target | QEMU에서 테스트 실행 | < 15min | 아키텍처 의존 버그(정렬, 엔디언, 타입 크기) |
| L4 image build | Yocto 이미지 | 시간 단위 | 통합·패키징 |
| L5 real device | 실기기 (이 저장소 범위 밖) | - | 타이밍, 드라이버, 하드웨어 |

## 합격 기준

1. 커밋 하나가 L0~L3를 자동으로 통과한다.
2. 각 단계의 **소요 시간이 아티팩트로 기록**된다.
3. 실패 시 **재현에 필요한 것이 한 덩어리로 남는다**
   (커밋 해시, 빌드 플래그, 로그, 산출물 해시).
4. 캐시가 단계 간에 공유된다 (L1이 채운 캐시를 L2가 쓴다).

## 사전 측정 — 컨테이너 빌드는 느린가 (2026-08-19)

파이프라인을 짜기 전에 "컨테이너로 빌드하면 느려지는가"를 먼저 쟀다.
같은 40 라이브러리 워크로드, 8코어. `docker/Dockerfile`(ubuntu:22.04 고정).

| 실행 방식 | clean 빌드 | 증분(무변경) |
|---|---|---|
| 호스트 | 15.49s | **0.16s** |
| 컨테이너 — 상주 + `docker exec` | 15.77s | **0.34s** |
| 컨테이너 — 매번 `docker run` | 19.65s | **4.24s** |
| 컨테이너 — 완전 콜드(첫 실행) | 27.95s | — |

1회성 비용: 이미지 빌드 **57초 / 1.08GB**.

**컨테이너 실행 자체의 오버헤드는 사실상 0이다** (15.77 vs 15.49, 노이즈 범위).
리눅스 컨테이너는 네임스페이스·cgroup이라 CPU 작업은 네이티브 속도로 돈다.

**느려지는 진짜 원인은 하나다: Bazel 서버를 잃는 것.**
`docker run`을 매번 새로 하면 그때마다 서버가 새로 뜨고 분석을 처음부터 한다
→ 증분 빌드가 0.34s에서 4.24s로 **12배**. clean 빌드에서는 상대적으로 묻히지만
개발 이터레이션에서는 이게 전부다.
**대응: 컨테이너를 상주시키고 `docker exec`로 들어간다.**

### 환경이 다르면 캐시를 공유하지 못한다

같은 원격 캐시를 두고 호스트(gcc 15.2)와 컨테이너(gcc 11.4)가 빌드했다.
캐시 서버 도달은 `/status -> 200`으로 확인했다.

| 빌드 주체 | 결과 |
|---|---|
| 호스트가 채운 캐시 → 호스트 | 82 remote cache hit |
| 호스트가 채운 캐시 → **컨테이너** | **0 hit** (42개 전량 재컴파일) |
| 컨테이너가 채운 캐시 → 컨테이너 | 42 remote cache hit |

액션 그래프 자체가 달랐다(호스트 82개 컴파일 액션 vs 컨테이너 42개) — 컴파일러가
다르면 툴체인 설정이 달라지고 액션 키가 달라진다.

**이게 실행 환경을 고정하는 실질적 이유다.** exp02에서 `PATH` 하나로 캐시가
전부 깨졌던 것과 같은 이야기가 한 층 위에서 반복된다. 개발자마다 배포판이 다르면
공유 캐시는 이름만 공유고 히트율은 0이다. 반대로 **모두가 같은 이미지를 쓰면
그때부터 캐시가 실제로 값을 한다.**

(다행히 오염은 없었다 — Bazel이 두 환경을 다른 키로 구분했다.)

### 컨테이너에서 걸린 것들

- **볼륨이 root 소유** → 비루트 사용자로 실행하면 `permission denied`.
  내가 소유한 호스트 디렉터리를 바인드 마운트하는 쪽이 간단하다.
- **`$USER` 미설정** → Bazel이 `FATAL: $USER is not set`으로 즉사한다.
  이미지에 없는 uid로 실행하면 `/etc/passwd` 조회가 실패하기 때문. `-e USER=...` 필요.
- **샌드박스가 `linux-sandbox` → `processwrapper-sandbox`로 강등**된다(권한 부족).
- ⚠️ **측정 함정**: 처음엔 실패한 빌드를 "0.44초"로 기록할 뻔했다.
  측정 스크립트는 **반드시 종료 코드를 확인**해야 한다.

## 알아둘 것

- **아래 계층의 신뢰도를 측정하라.** "L3까지 통과했는데 L5에서 깨진 비율"을 추적하지 않으면
  계층 설계는 그냥 믿음이다. 이 숫자가 있어야 "L3 통과 = 배포 가능"을 주장할 수 있다.
- 재현 번들이 없으면 실패한 CI는 정보가 아니라 알림일 뿐이다.
- GitHub Actions 경험이 있다면 개념은 그대로 옮겨진다. 다른 건 러너 모델
  (executor 종류)과 캐시/아티팩트의 수명 관리다.
- 파이프라인 자체의 메트릭(큐 대기 시간, 실패율, flaky 비율)을 수집하는 것이
  DevOps의 실제 산출물이다.
